# ADR-0004：模拟世界，以及它证明什么、不证明什么

- 状态：已采纳（M1）
- 相关章节：主设计 §26、§27.2、§28；计划决定 D6、D9

## 背景

真实后端依赖 M0/M2 的结论（ScreenCaptureKit、AX、CGEvent、事件 tap、Laya、教师模型、S2 路线）。M1 要在它们到位前验证架构，又不能让模拟结果被误读成真机结果。

## 决定

- 所有后端都是模拟的，并且如实报告：`cu-device` 目前只有模拟后端（没有后端开关，M2 加入真实后端时再引入），能力清单写 `backend: simulated`；`cu-source` 是夹具来源；规划器与教师是脚本化的确定性替身，不是模型。
- 模拟世界是一个**设置应用**（两个页面、同名开关分在两个分组、Apply 与保存状态、模态对话框），由一份 append-only 世界日志驱动：设备写输入，来源重放日志，所以两个进程在不共享内存的情况下看到同一个应用。测试可以往日志里追加“弹出对话框”。
- 不启动 Electron 窗口（避免在用户桌面上弹窗与抢焦点）：Electron 壳用类型检查、构建和对真实原生进程的 Node 级测试验证。

## 这套验证证明了什么

- 架构的各个接缝成立：契约、状态机、单事务接纳、证据先于结论、停止与恢复、进程间协议、三条停止入口。
- 一批具体的失败路径有确定的、可重复的行为：停止先到设备、人工输入暂停与显式 resume、设备被杀、重启不重放、后端不可用时等待、幻觉出的候选被拒绝、动作前的帧不能证明效果、租约缺失。

## 这套验证不证明什么

- **S1 决策质量**：教师替身按固定偏好选择，回答不了 Laya 是否够用（§8.6）。这仍是整个架构最大的未知数，应与本阶段并行开始。
- 真实设备行为：AX 超时与无响应、坐标与遮挡、事件 tap 的可靠性、TCC 权限、签名包。
- 时延、性能、睡眠与时钟行为、断电下的 SQLite 持久性（只验证了进程级重启）。
- Electron 在真实窗口里的行为：沙箱、CSP、preload 与托盘/全局热键。这些代码经过类型检查和构建，但没有在 Electron 里运行过。
- 已实现的技能只有 read_value、ensure_value、activate、revisit；enter_text、scroll_to、activate_window 在契约里登记但没有运行时，计划校验因此不接受它们。TextEdit 环境包没有做。

## 后果

任何引用 M1 结果的文档或报告都必须带上这些边界；`UiProjection.capabilities.backend` 为 `simulated` 时，界面显示“Simulated device”。
